## 3. The backplane-cost interpretation (important — this is a better result, not a worse one)

The paragraph after Table IV currently reads that the backplane adds 0.69 ms, "about
6.8 % over local delivery". Two things are wrong with it: the number, and the word
*local*.

With a message queue configured, **every** emit traverses Redis — Flask-SocketIO has no
faster in-process path once a queue is attached. So the same-instance row is not a local
baseline; both rows are Redis round-trips, which is exactly why they differ by 0.36 ms
(2.0 %), within run-to-run noise.

Suggested replacement:

> Both paths cross the backplane: once a message queue is attached, Flask-SocketIO routes
> every emission through it, so the same-instance figure is not an in-process baseline.
> The two paths differ by 0.36 ms, about 2 % and within run-to-run variance, which says
> that fan-out to a second instance is not what costs the time — the traversal itself is.
> The paths diverge only when the backplane fails, which Section C measures.

This is a stronger claim than the one it replaces and it survives scrutiny at the viva,
where "how did you get a local baseline with a queue configured?" is an obvious question.

## 5. Table V — add a latency column, and a new finding

```
| Probe                                   | Redis up   | Redis down            |
|-----------------------------------------|------------|-----------------------|
| `/health` (load balancer, matcher 200)  | 200, 0.01 s| 200, **7.53 s**       |
| `/ready`  (operators, dashboards)       | 200, 0.01 s| 503, **12.74 s**      |
```

(Second instance: `/health` 4.78 s, `/ready` 19.17 s. After recovery both probes return
200 in under 0.04 s.)

Then add this paragraph — it is the single most valuable thing the run produced:

> The split behaves as designed on status code, but not on time. With the cache stopped,
> `/health` still answers 200, yet it takes 7.53 s to do so because the client library
> exhausts its retry budget before the handler returns. The load balancer's health-check
> timeout is 5 s, and a probe that exceeds it is recorded as a failure regardless of the
> status code it would eventually have produced. The correction to D3 is therefore
> necessary but not sufficient: the fleet-replacement failure mode it was written to
> remove is still reachable through latency rather than through status. We record this as
> D11. The remedy is a bounded timeout on the dependency check inside the handler, so the
> probe answers within the load balancer's budget whatever the dependency is doing.

Also correct the sentence after Table V: cross-instance delivery stopping at 0 of 10 and
same-instance continuing at 10 of 10 is confirmed, but drop *"and all 10 messages were
still persisted"* (not measured in that run). Add instead:

> All three WebSocket clients were disconnected when the cache stopped, so the loss is
> not confined to cross-instance fan-out: connected sessions are dropped and must
> reconnect.

```
| 45 s          | t + 0.69 s           | t + 15.19 s      | 14.5 s  |
```

Footnote f becomes: *The window tracks the backoff reached during the outage; the log
reports a 32 s retry ceiling, and the measured windows sit below it.*

Everywhere D8 is described as a window "of up to 32 s", say instead: *measured at 1.2 s
after a 5 s outage and 14.5 s after a 45 s outage, against a 32 s retry ceiling in the
log.* The defect reproduced on both runs and scaled with outage length, which is what the
backoff explanation predicts — say so; it is evidence, not a detail.

## 7. Table VII — three new defects

Append:

```
| D9  | Dependency-resolution drift | An unpinned transitive dependency (SQLAlchemy, pulled in by Flask-SQLAlchemy) resolved to a version whose default driver for a bare `postgresql://` URI is psycopg 3, which the image does not ship. The worker fails to start against PostgreSQL while every unit test passes on SQLite. | Fixed |
| D10 | Runtime library incompatibility | eventlet replaces the standard library resolver with a green implementation that could not resolve the cache hostname; the lookup times out after roughly 20 s, while psycopg2 — a C extension eventlet never patches — resolves the database normally. The publish/subscribe backplane is lost silently, with nothing in the log. | Fixed |
| D11 | Probe latency under dependency failure | With the cache stopped, `/health` returns 200 but takes 7.53 s, exceeding the load balancer's 5 s health-check timeout. The fleet-replacement failure mode that the D3 correction removed on status code remains reachable on time. | Open |
```

Footnote g: *None of the eleven was detectable by any instrumented verification layer.*

Intro to the section: *Seven were found by reading the code after every automated gate
was green. Four more were found only by running the system.*

Add a fourth group to the three-group analysis:

> **Defects that exist only in a running process.** D9, D10 and D11 are invisible to
> every layer in Table II and to all 168 unit tests, because the tests exercise the
> application against SQLite and an in-process transport rather than against the
> containerised dependencies it will actually have. D9 is a version resolved at build
> time, D10 an interaction between a concurrency library and a C extension, D11 a
> property of elapsed time. None is a statement about the configuration, so no analysis
> over the configuration can reach them. This is the sharpest form of the paper's claim:
> the gap is not merely between well-formed and correct, but between a system described
> and a system started.

D9 and D10 also make a point worth one sentence: they stopped the application from
starting at all, and they were found the first time it was run. Everything else had been
green for weeks.
